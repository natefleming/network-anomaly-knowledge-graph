# Network-Traffic Anomaly Knowledge Graph

End-to-end Databricks demo: a Spark Declarative Pipeline that builds a **knowledge graph** of network traffic from raw flow logs, surfaces five distinct anomaly patterns (port scan, lateral movement, data exfiltration, rogue device, DDoS) as materialized views, and ships with a **React + react-force-graph-2d** Databricks App that lets you visually explore, search, and inspect the graph.

Built as a Declarative Automation Bundle (`bundle.engine = direct`) targeting Serverless v5 on the `fevm` profile.

---

## Quick start

```bash
cd <path-to-this-repo>

# 1. Validate
DATABRICKS_BUNDLE_ENGINE=direct databricks bundle validate -p fevm

# 2. Deploy (catalog grants + schema + volume + pipeline + 4 jobs + app + 3 notebooks)
DATABRICKS_BUNDLE_ENGINE=direct databricks bundle deploy -p fevm

# 3. Generate the bronze SQL files (notebook 00 — only first time, or to refresh data)
databricks bundle run generate_bronze_sql -p fevm

# 4. Load bronze + run the SDP pipeline (notebook 01 → pipeline task)
databricks bundle run load_bronze -p fevm

# 5. Start the app
databricks bundle run network_anomaly_app -p fevm
```

## Knowledge graph schema

The graph is **two Delta tables**. Each entity type carries its own attribute payload as a Databricks **`VARIANT`** column — schema-less per-type metadata, queried with the `attrs:field::type` extraction operator. No joins back to bronze are needed for entity properties.

### `gold_graph_nodes` — every entity in the graph

Liquid-clustered on `(node_id, node_type)` so the app's `/api/node/{id}` endpoint and node-type filters seek directly.

| Column | Type | Description |
|---|---|---|
| `node_id` | STRING | Typed primary key, e.g. `host:H-0207`, `subnet:SUB-005`, `service:SVC-0142`, `ext:185.220.101.42` |
| `node_type` | STRING | `host` \| `subnet` \| `service` \| `external_ip` |
| `label` | STRING | Human-readable name (hostname, CIDR, service_name, external IP) |
| `attrs` | **VARIANT** | Per-type attribute payload — see the table below |
| `criticality` | INT | 1–5; only populated for `host` rows |
| `subnet_id` | STRING | For hosts and subnets — null otherwise |
| `is_external` | BOOLEAN | True for external_ip nodes and external-zone subnets |
| `host_type` | STRING | `workstation` \| `server` \| `gateway` \| `iot` \| `subnet` \| `service` \| `external` |
| `anomaly_score` | DOUBLE | Max score across all detectors that flagged this node (0–1) |
| `anomaly_labels` | ARRAY&lt;STRING&gt; | List of anomaly types that flagged this node |

**Per-type VARIANT `attrs` payloads:**

| node_type | Sample attrs fields |
|---|---|
| `host` | `host_id`, `ip`, `host_type`, `os`, `owner`, `criticality`, `subnet_id`, `zone`, `cidr`, `is_external`, `last_active_ts`, `flow_total` |
| `subnet` | `subnet_id`, `cidr`, `zone`, `description` |
| `service` | `service_id`, `host_id`, `host_type`, `port`, `protocol`, `service_name` |
| `external_ip` | `ip`, `total_bytes`, `flow_count`, `distinct_internal_callers`, `last_seen_ts` |

### `gold_graph_edges` — every relationship in the graph

Liquid-clustered on `(src_id, dst_id, edge_type)` to support the app's neighbor lookups (`/api/node/{id}` joins back here) and the detectors' edge_type-scoped filters.

| Column | Type | Description |
|---|---|---|
| `src_id` | STRING | Source node id (matches `gold_graph_nodes.node_id`) |
| `dst_id` | STRING | Destination node id |
| `edge_type` | STRING | `flow` \| `resolves` \| `hosts` \| `in_subnet` |
| `packet_count` | BIGINT | Aggregated packets for flow edges, query count for resolves |
| `byte_count` | BIGINT | Aggregated bytes for flow edges |
| `flow_count` | BIGINT | Number of flows/resolves between this src/dst pair |
| `is_cross_zone` | BOOLEAN | True if src and dst are in different security zones |
| `is_anomalous` | BOOLEAN | True if this edge participates in any anomaly |
| `anomaly_label` | STRING | Which anomaly type, when `is_anomalous = true` |
| `anomaly_score` | DOUBLE | Score 0–1 |
| `last_seen_ts` | TIMESTAMP | Most recent observation in the source data |
| `attrs` | **VARIANT** | Edge-type-specific payload — see below |

**Per-edge-type VARIANT `attrs` payloads:**

| edge_type | Endpoints | What it represents | Sample attrs fields |
|---|---|---|---|
| `flow` | `host:* → host:*` or `host:* → ext:*` | Network traffic, aggregated by (src,dst) | `src_zone`, `dst_zone`, `is_cross_zone`, `is_dst_external`, `packet_count`, `byte_count`, `flow_count`, `distinct_dst_ports[]`, `distinct_protocols[]`, `avg_duration_ms`, `last_seen_ts` |
| `resolves` | `host:* → ext:*` | DNS resolution from a host to an IP | `query_count`, `sample_queries[]` (first 5), `query_types[]`, `is_suspicious_tld`, `last_seen_ts` |
| `hosts` | `service:* → host:*` | "Service runs on host" | `port`, `protocol`, `service_name` |
| `in_subnet` | `host:* → subnet:*` | "Host belongs to subnet" | `zone`, `cidr` |

### Anomaly materialized views

Each of the five anomaly types is a separate MV under `pipelines/gold/`, joined back into `gold_graph_nodes.anomaly_labels` and `gold_graph_edges.anomaly_label` by `node_id`. Each MV also carries an `evidence` JSON column with the supporting data for the analyst.

| Table | Granularity | Columns |
|---|---|---|
| `gold_anomaly_scan` | one row per (host, 10-min window) when port-scan detected | `node_id`, `src_host_id`, `src_hostname`, `window_start`, `window_end`, `distinct_dests`, `distinct_ports`, `flow_count`, `score`, `evidence` |
| `gold_anomaly_lateral` | one row per lateral-movement chain | `node_id`, `origin_host_id`, `chain[]`, `zone_chain[]`, `start_ts`, `end_ts`, `score`, `evidence` |
| `gold_anomaly_exfil` | one row per (host, external_ip, 5-min window) | `node_id`, `src_host_id`, `src_hostname`, `external_dst_ip`, `window_start`, `window_end`, `total_bytes`, `flow_count`, `score`, `evidence` |
| `gold_anomaly_rogue` | one row per rogue host | `node_id`, `host_id`, `hostname`, `flow_count`, `suspicious_query_count`, `score`, `evidence` |
| `gold_anomaly_ddos` | one row per (target, 5-min window) | `node_id`, `dst_host_id`, `dst_hostname`, `window_start`, `window_end`, `distinct_sources`, `flow_count`, `score`, `evidence` |

## Anomaly types demonstrated

All five are computed from the same nodes + edges. Each is a single materialized view in `pipelines/gold/`, under 40 lines of SQL.

### 1. Port scan — `gold_anomaly_scan`
**Pattern:** one host fans out to many destinations on many distinct ports in a short window — the classic Nmap-style reconnaissance signature.

**Detection rule:**
- ≥ 30 distinct destination hosts **AND**
- ≥ 30 distinct destination ports **AND**
- Within a single 10-minute tumbling window

**Visual signature in the app:** a starburst — one red glowing node with edges radiating out to dozens of distinct neighbors.

**Seeded example:** `H-1027` hits 60 destinations on 6 ports each in a 3-minute window.

---

### 2. Lateral movement — `gold_anomaly_lateral`
**Pattern:** a multi-hop chain of cross-zone flows where each hop becomes the source of the next, crossing security zones an attacker would not normally traverse.

**Detection rule:**
- Built via 3 self-joins on cross-zone flows: `a.dst = b.src`, `b.dst = c.src`
- All hops within a single 15-minute window
- ≥ 3 distinct zones visited across the chain (e.g. corporate → iot → dmz → corporate)

**Visual signature in the app:** a snake of red edges connecting nodes across different subnets that should never communicate directly.

**Seeded example:** 3 chains, e.g. `H-1717 → H-0344 → H-1429 → H-1636`.

---

### 3. Data exfiltration — `gold_anomaly_exfil`
**Pattern:** large outbound flow from an internal host to a single external IP, with byte volume dramatically asymmetric.

**Detection rule:**
- Outbound flow to an external destination IP
- Total bytes > 5 MB
- Within a 5-minute window per (source, external_ip) pair

**Visual signature in the app:** a thick red edge from one internal node to an external_ip node, with fast-moving animated packet particles flowing outward.

**Seeded example:** `H-1793` sends ~25 MB to `185.220.101.42` over 20 bursts in 4 minutes.

---

### 4. Rogue device — `gold_anomaly_rogue`
**Pattern:** an internal host that has **zero** traffic peers in the entire dataset AND makes DNS lookups to suspicious top-level domains. Real workstations make hundreds of flows per day; silence + sketchy DNS is highly anomalous.

**Detection rule:**
- Internal host (`is_external = false`)
- `flow_count = 0` across all observed traffic
- AND ≥ 1 DNS query to a flagged TLD (`.xyz`, `.top`, `.tk`, `.click`, `.ru`, `.pw`, `.cc`, `.bid`)

**Visual signature in the app:** purple isolated node floating at the periphery of the graph — connected only by `resolves` DNS edges to external IPs.

**Seeded example:** 5 rogues — `H-0000`, `H-0005`, `H-0006`, `H-0009`, `H-0010` — each with 8 suspicious-TLD lookups and zero peer flows.

---

### 5. DDoS target — `gold_anomaly_ddos`
**Pattern:** a single internal host receiving traffic from a large number of distinct sources within a tight time window — the fan-in signature of a distributed denial-of-service.

**Detection rule:**
- ≥ 50 distinct source hosts hitting the same destination
- Within a single 5-minute tumbling window

**Visual signature in the app:** the highest-degree-centrality node in the graph, visually overwhelmed with edges fanning IN from every direction.

**Seeded example:** `H-1447` receives traffic from 150 distinct sources in a 5-minute window — appears at the top of the GraphFrames degree-centrality ranking (degree 195).

---

### Bonus: suspicious DNS — flagged on `gold_graph_edges`
**Pattern:** DNS-resolution edges where the queried domain matches a flagged TLD list. Surfaced on edges (not nodes) because the anomaly lives in the relationship — host A asking for `something.xyz` is the signal.

**Where it lives:** `gold_graph_edges` where `edge_type = 'resolves'` and `attrs:is_suspicious_tld::boolean = true`.

## OCSF alignment

The event-shaped bronze tables (network flows + DNS queries) conform to the **Open Cybersecurity Schema Framework**. Each event row carries `class_uid`, `activity_id`, `type_uid`, and `severity_id`, and the column names map directly to OCSF fields:

| Table | OCSF class | class_uid | type_uid | Column → OCSF mapping |
|---|---|---|---|---|
| `bronze_network_flows` | Network Activity | 4001 | 400106 | `time` → `time`, `src_host_id` → `src_endpoint.uid`, `dst_host_id` → `dst_endpoint.uid`, `dst_ip` → `dst_endpoint.ip`, `src_port`/`dst_port` → `src_endpoint.port` / `dst_endpoint.port`, `protocol_name` → `connection_info.protocol_name`, `traffic_packets` → `traffic.packets`, `traffic_bytes` → `traffic.bytes`, `duration` → `duration` |
| `bronze_dns_queries` | DNS Activity | 4003 | 400301 | `time` → `time`, `src_host_id` → `src_endpoint.uid`, `query_hostname` → `query.hostname`, `query_type` → `query.type`, `rcode_id` → `rcode_id`, `answer_ip` → `answers[0].rdata` |

The entity tables (`bronze_hosts`, `bronze_subnets`, `bronze_services`) align with OCSF **Device**, **Network**, and **Service** objects via column comments. Every column in every silver/gold MV carries its OCSF mapping in its `COMMENT` so the UC Explorer and Genie show the standard names alongside our local ones. Silver maintains short aliases (`ts`, `bytes`, `packets`, `protocol`) alongside the OCSF names so downstream detector SQL stays readable.

## Bronze → silver → gold flow

```
data/*.sql (committed)
  └─ notebook 01 (WorkspaceClient.statement_execution.execute_statement)
       └─ bronze_subnets, bronze_hosts, bronze_services, bronze_network_flows, bronze_dns_queries
            └─ SDP pipeline (Serverless v5)
                 ├─ silver_hosts, silver_services, silver_flows, silver_dns
                 └─ gold_graph_nodes  ◄──┐
                    gold_graph_edges  ◄──┤── joined back from anomaly_labels / anomaly_label
                    gold_anomaly_{scan, lateral, exfil, rogue, ddos}
```

All gold and silver tables use **Liquid Clustering** tuned to their actual join patterns. Bronze tables enable `delta.enableRowTracking = true` so MV refresh can be incremental.

## Layered performance tuning

| Concern | Approach |
|---|---|
| **Join keys** | Liquid clustering on every table's actual join columns (e.g. `silver_flows` → `(src_host_id, dst_host_id, ts)`) |
| **MV refresh** | `delta.enableRowTracking = true` on bronze enables incremental MV refresh |
| **Change consumers** | `delta.enableChangeDataFeed = true` on bronze for downstream CDC |
| **Small dimensions** | `bronze_subnets` (24 rows) intentionally unclustered — broadcasts in joins |
| **Anomaly join-back** | `gold_anomaly_*` clustered by `node_id` so `gold_graph_nodes` joins them cheaply |

## The Databricks App

- **Stack:** React 18 + Vite + TypeScript + `react-force-graph-2d` (canvas), FastAPI (Python) backend, deployed as a Databricks App
- **Visualization:** color-coded nodes (blue=normal, green=server, yellow-pulsing=elevated, red-glowing=confirmed, purple=rogue), animated packet particles along flow edges, edge labels showing relationship type on incident edges
- **Interaction:** search (highlights matching nodes), click a node (focus mode dims non-neighbors), click an edge (drawer flips to edge details), drag side panel handles to resize, three toolbar buttons (Re-center, Clear filters, Reset graph)
- **Data sources panel:** collapsible bronze/silver/gold groups with deep links into Unity Catalog Explorer for every table
